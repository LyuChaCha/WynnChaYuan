# 加入翻譯團隊

> **動手翻任務之前先讀 [世界觀與主線](world-and-story.md)。** 同一個詞在
> 不同任務裡指的是不是同一件事，決定了譯文能不能對得起來。

## 先聯繫 LyuChaCha

**動手翻之前，請先連絡 LyuChaCha。**

不是為了審核你，是為了避免「各翻各的」：同一個詞兩個人翻成兩種說法，
玩家會以為是兩個不同的東西；兩個人同時翻同一個檔案，合併時還會互相覆蓋。
先講一聲，就能分配到還沒有人動的部分。

- GitHub：[@LyuChaCha](https://github.com/LyuChaCha)
- 或在 [Issues](https://github.com/LyuChaCha/WynnChaYuan/issues) 開一則說一聲

## 需要具備的能力

**看得懂英文、能用中文表達。**

- 英文**不用精通**。Wynncraft 的文本大多是簡單的敘述句，
  查得到、看得懂就夠了。
- 中文要能寫出讓人一眼看懂的句子。這比英文程度重要——
  翻得「正確但拗口」，玩家還是看不懂。
- **不需要會寫程式。** 翻譯檔是純 JSON，在 GitHub 網頁上點鉛筆就能改。

真正需要的是**願意查證**：不確定一個詞在遊戲裡指什麼，就進遊戲看一眼，
或到 [wiki](https://wynncraft.wiki.gg/) 查。照字面翻在 Wynncraft 上很容易錯
（`Reflection` 是「遠程反傷」不是「反射」），這類詞都整理在
[GLOSSARY.md](../GLOSSARY.md)。

## 開始之前

1. 連絡 LyuChaCha，確認要接哪一塊
2. 讀 [CONTRIBUTING.md](../CONTRIBUTING.md)——佔位符、換行、格式檢查
3. 讀下面「最近的幾個改動」——有些規則跟你想的不一樣

# 最近的幾個改動

這幾版改了一些會直接影響你怎麼填譯文的東西。**下面五件事會讓你少做很多工**，
或者避免翻了卻不生效。

完整規則仍以 [CONTRIBUTING.md](../CONTRIBUTING.md) 為準，這份只講「有什麼變了」。

---

## 一、技能名稱只要翻一次

技能說明裡到處都在提別的技能：

```
Bash will hit a second time at a farther range.
```

**不要逐條翻那個 `Bash`。** 把 `ability.json` 裡 `Bash` 那一條的**名稱**翻好，
所有提到它的敘述都會自動換成譯名。

所以在敘述裡看到技能名稱時，**原樣留著英文**：

```json
"src": "Bash will hit a second time at a farther range.",
"dst": "Bash 會增加範圍並攻擊兩次。"
```

畫面上出現的會是「**重擊** 會增加範圍並攻擊兩次。」

### 為什麼不用 `warrior-1-1-5` 這種代號

團隊先前提過用技能樹的座標當代號。方向是對的，但座標是**節點在畫面上的位置**——
Wynncraft 每次改版都在挪節點，挪一個，所有引用就全錯了。而且在語料裡看到
`Bash` 一眼就懂，看到 `warrior-1-1-5` 只能去查表。

用名稱當參照效果一樣，代價小得多，而且**語料完全不用改**。

### 範圍

- 只認 `ability.json` 與 `major-id.json` 的名稱。裝備名稱不會這樣被替換。
- 四個字元以下的不換（`Aid`、`Ice` 這種在一般句子裡到處都是）。
- 必須大寫開頭、而且是完整的詞。`you bash the ground` 不換，
  `Bashful grin` 也不換。

## 二、一句裡有兩個以上的數值

### 怎麼知道哪個是哪個

**照順序**：譯文裡第一個 `{~}` 拿原文的第一個數值，第二個拿第二個。

每一條都有 `_raw` 欄位，那是**還沒抽掉數字**的原文，對照著看就知道誰是誰：

```json
"src":  "Allies within {~} blocks gain {~} of the health you gain...",
"_raw": "Allies within 16 blocks gain 100% of the health you gain...",
"dst":  "{~} 格內的友軍會獲得你從……取得的 {~} 生命值"
```

第一個 `{~}` 是 `16`，第二個是 `100%`。

### 語序要調換的時候

中文語序常常跟英文相反。用 **`{~1}` `{~2}`** 指名要第幾個：

```json
"src": "+{~} to {~}",
"dst": "最多 {~2}，最少 {~1}"
```

沒有編號的維持照順序，兩種可以混用。編號從 **1** 開始，最多到 9。

## 三、詞條有三種寫法，不要混

**這一段來回改過四次，每改一次遊戲裡就錯一輪。照這張表填，不要自己改規則。**

| 英文標籤 | 什麼時候出現 | 中文 | 例 |
|---|---|---|---|
| `X` | 實數與百分比**都會用到**這個標籤 | 名稱 | `火屬性傷害` |
| `X%` | 我們的機制：數值帶 `%` 時優先查這個 | 名稱 + `百分比` | `火屬性傷害百分比` |
| `X Raw` | 英文自己就寫了 Raw | 名稱 + `值` | `火屬性傷害值` |

```json
"Fire Damage":     "火屬性傷害",
"Fire Damage%":    "火屬性傷害百分比",
"Fire Damage Raw": "火屬性傷害值"
```

### 兩個最常犯的錯

**`X` 千萬不要寫成「…百分比」。** 遊戲裡 `Thunder Damage: +1-8` 這種**實數**
走的也是 `X`，寫成百分比就會看到「雷屬性傷害百分比 +1-8」。

**`X%` 中間不能有空格。** 寫成 `"Fire Damage %"` 永遠比對不到——機制是直接在
標籤後面接 `%`。

### 什麼時候才該加 `X%`

只在**真的兩種都有**的時候。近戰反傷、遠程反傷本來就只有百分比；魔力回復、
生命竊取、中毒本來就只有實數。多開一個只會讓後面的人以為遊戲裡真的有兩種。

判斷依據：**遊戲裡看得到 `X Raw` 這個標籤，就代表兩種都有。**

法術消耗（`Meteor Cost` 那類）已經補齊 24 組。法術名的中文是照現有風格填的，
**看到不順的直接改一行就好**。

## 四、譯文的換行不必跟原文一樣

中文比英文緊湊，原文分兩行的句子往往一行就講完。先前系統會要求行數一致，
硬湊會斷在莫名其妙的地方——那個限制**拿掉了**。

佔位符改成**整段照順序**取用，所以把 `{~}` 搬到上一行、或把兩行併成一行都可以，
只要整段的數量對得上。

## 五、任務對話會照任務與 NPC 分堆

收集對話時會一併記下**當下追蹤的任務**與**玩家正對著的 NPC**，合併之後同一段
劇情的台詞會排在一起，並插入分段標題：

```json
"_── Cook Assistant · Aledar ──": "",
"Hey there, traveller!": "",
"I need your help with something.": ""
```

**底線開頭的鍵是給人看的分段標題，不要翻，也不要刪。** 程式會自動跳過它們。

NPC 是用「玩家正前方最近的名牌」猜的，旁邊站著別人時可能記錯。它只影響排序，
不會影響譯文。

要重新收集才會有這些標籤——既有的條目沒辦法回溯補上。

## 六、任務對話已經從 wiki 抓下來了

先前要有人真的把 158 個任務全部跑一遍才收得到對話。現在
`quest-dialogue.json` 直接取自 [Wynncraft wiki](https://wynncraft.wiki.gg/)（**22,088 句**），
**照任務與階段排好，而且每一句都標了說話的人**：

```json
"Cook Assistant#004": {
  "src": "Unfortunately, a Grook took my last cake, and I ran out of ingredients!",
  "dst": "",
  "quest": "Cook Assistant",
  "stage": "Stage 1",
  "speaker": "The Cook"
}
```

鍵是「任務#序號」，所以同一段劇情**天然排在一起**，從頭翻到尾就好。

**一個任務一個檔案**，放在 `translations/quest/` 底下，接了哪個就開哪個，
不會跟別人在同一個檔案裡打架。

> `quest-dialogue.json` 是**產生物**，合併之後由 CI 自動重新產生。
> **不要改它**，也不用管它——改你的任務檔就好。

要接哪一個任務，看 **[任務對話認領清單](quest-dialogue.md)**——那裡有每個任務
幾句、翻了多少，還有「適合第一次接的」小任務清單。**動手前先講一聲。**

> **注意**：wiki 是人寫的，跟遊戲裡的字串<b>不保證逐字相同</b>——標點、
> 大小寫都可能有出入，對不上的話遊戲裡就不會生效。所以它的定位是
> 「先把量做起來、讓你看得到上下文」；實際跑過遊戲收集到的句子會蓋掉它。
>
> 翻的時候發現跟遊戲裡不一樣，**以遊戲裡的為準**，直接改 `src`。

## 七、顏色不對的時候，可以直接寫出來

譯文的顏色平常是**猜**的：拿原文有顏色的那一段，到譯文裡找一樣的字面。
技能名、地名這種保留原文的詞找得到；**翻成中文的就找不到**，那一段掉回底色。
整行只有一個顏色還救得回來（照位置對），一行混了兩三種顏色就沒辦法。

猜不到的時候，只有你知道答案，所以可以直接寫：

| 寫法 | 意思 |
|---|---|
| `{c1}`–`{c9}` | 用原文的第 N 個顏色（依第一次出現的順序） |
| `{c:#FF55FF}` | 自己指定色碼 |
| `{c:gold}` | 自己指定原版顏色名稱（Minecraft 那十六個） |
| `{/}` | 到此為止，回到這一段原本的顏色 |

```json
"src": "[Cave Completed]\nGrook's Nest\n- Rewards:",
"dst": "{c1}[洞穴完成]{/}\n{c2}Grook 巢穴{/}\n{c3}- {c4}獎勵：{/}"
```

三件要記得的事：

- **只寫在譯文**。`src` 那半是遊戲送來的字，寫進去那條就永遠查不到了。
- 一個 `{cN}` 管到 `{/}` 或下一個 `{cN}` 為止，**可以跨行**——
  一句話被切成兩行時，在第一行開色段就能一路染到第二行。
  想染到這一條的結尾就直接不寫 `{/}`。
- 編號超出範圍**當作沒寫**，那一段回去走猜的那條路。顏色不對可以忍，
  整行不顯示不行。

哪個編號是哪個顏色，看診斷檔 `config/wynnchayuan/majorid-debug.txt` 的
「可用的顏色」那一段（F6 打開診斷才會寫）。完整說明見
[CONTRIBUTING.md](../CONTRIBUTING.md)。

## 送出前

```bash
python tools/validate.py
```

它擋的是**無論翻得好不好都一定錯**的東西：佔位符數量、材質包符號、地名被翻掉。
翻得對不對機器判斷不了，那需要人看。

送 PR 時 CI 會跑同一支程式，錯誤必須修掉才能合併；警告請自己判斷是不是刻意的。

## 遇到版面問題怎麼回報

`config/wynnchayuan/` 底下有兩個檔案，附上去比截圖有用得多：

| 檔案 | 什麼時候看 |
|---|---|
| `line-debug.txt` | 翻到了但版面怪怪的 |
| `layout-debug.txt` | 整塊沒有跟著置中／對齊 |

`tooltip-debug-*.json` 則是「明明填了譯文卻沒生效」時用的——裡面是遊戲實際拿去
查表的樣子，跟語料的 `src` 比對就知道差在哪。
